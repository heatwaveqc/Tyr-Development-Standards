# Work management
Maintain canonical ledger with (1) implementation-ready slices: approved behavior, acceptance criteria, owner, dependencies, PR and state ready/in progress/source-ready/integrated; (2) explicit owner design blockers: exact question, affected slices and decision owner; (3) pending runtime acceptance: setup, expected behavior, status and evidence. Update after decisions, coding and handoff. Do not hide ready slices behind mixed-status parents or confuse engineering investigation, QA or dependency issues with design blockers.
Live chats favor design decisions when selecting work but execute explicit implementation requests. Scheduled work favors approved unclaimed current-sprint slices, respecting configured eligibility; check duplication and escalate unresolved design. Before claiming nothing to code reconcile issues, decisions, branches and implementation. Report active workstreams, integration-ready, integrated awaiting QA and cleanup debt separately; include PR opened/merged/closed-unmerged/net over interval. Audits execute authorized safe closures or record exact blocker, owner and next review.

## Mandatory GitHub status vocabulary

Use these exact searchable labels on issues and pull requests. They express evidenced work state, not priority, approval authority, branch mergeability, or release status. Preserve unrelated type, priority and subsystem labels. Each independently actionable slice has one current status; transitions replace its old status, not accumulate historical labels.

| Label | Meaning / entry gate | Applies to |
| --- | --- | --- |
| `status: needs-triage` | Scope, ownership, or next action has not yet been sufficiently evaluated. | Issue / PR |
| `status: needs-decision` | A specific unresolved owner design/scope/balance choice prevents the next action; record question, options/constraints, affected slice and decision owner. | Issue / PR |
| `status: needs-research` | A specific technical investigation or missing evidence is needed before proceeding; record deliverable and owner. | Issue / PR |
| `status: ready-to-code` | Requirements approved, bounded acceptance criteria and dependencies understood, implementation can begin; not currently claimed. | Issue / PR |
| `status: coding` | A named writer has claimed the slice and is implementing it on its identified workstream. | Issue / PR |
| `status: blocked` | A concrete engineering/external dependency prevents the next action; record dependency, owner, unblock condition, and next review. | Issue / PR |
| `status: needs-review` | Implementation or other scoped deliverable is present; verification/review required for source readiness remains outstanding. | Issue / PR |
| `status: ready-for-integration` | Independently coherent owner-approved source scope verified at exact current head, applicable quick checks satisfied, target/dependency order and handoff recorded; eligible for designated writer integration review. | Issue / PR |
| `status: awaiting-build` | Source integrated into the required target baseline, pending an available appropriately authorized build or equivalent runtime-test prerequisite. | Issue |
| `status: ready-for-qa` | Required exact candidate and setup available, acceptance case executable under applicable QA authorization. | Issue |
| `status: complete` | All acceptance criteria for this scope satisfied with evidence; close completed issue. | Issue |
| `status: deferred` | Intentionally postponed within owner-approved scope/priorities; record reason and revisit condition. | Issue / PR |

Repositories adopting this revision must establish these labels (colors are cosmetic; exact names and meaning are mandatory) and reconcile existing open work using live evidence. If label administration or verification is unavailable, record the exact label in the current description/ledger as a temporary fallback, report the capability blocker and arrange authorized reconciliation; do not claim labels were applied without verification. Do not delete or overwrite unrelated labels.

## Deferred work and automatic reactivation

For every deferred issue, PR or independently actionable slice, record the current status, reason, reactivation date (ISO `YYYY-MM-DD`, or `none`), reactivation condition (verifiable event, `manual owner approval`, or `none`), and intended reactivation status using the existing vocabulary. Record release target separately; it is not a reactivation trigger. Example:

- Status: `status: deferred`
- Reactivation date: `2026-11-27`
- Reactivation condition: `none`
- Reactivation status: `status: needs-decision`
- Reason: owner-approved post-preview work

If both a date and a condition are specified, both must be satisfied. A date becomes eligible at the start of that date in the project's declared timezone (record timezone if not established); a manual approval condition requires explicit owner authorization. Never invent dates or approvals for legacy holds. If intent is unclear, record an unresolved condition and request clarification through normal triage, without activating the work. Keep metadata at slice level for mixed parents; link corresponding PRs to avoid duplicate activation.

The designated backlog/ledger reconciliation owner (or existing scheduled reconciliation agent) checks due deferred work on each normal cycle; no separate automation or new status labels are required. Verify the current open item, latest owner instruction, trigger evidence (for example exact dependency merge or compatible published version), ownership, dependencies, supersession and current source/check state. If the trigger is satisfied, replace the deferred status with the intended status **only if its entry criteria are met**, otherwise use the actual evidenced actionable status (e.g. needs-triage, needs-research, needs-decision or blocked). Record the date, evidence, prior/new state and next owner/action in the item and canonical ledger, reconcile parent projections and notify the responsible writer. Do not reactivate closed or superseded items or overwrite a newer hold. If the trigger is not satisfied or cannot be verified, keep the deferral, record the blocker and next review. Repeated runs must be idempotent.

Reactivation makes a slice eligible for normal prioritization, not an automatic coding claim, merge, build, release, destructive action or permission to expand approved scope. Existing writer, evidence, QA and local authorization gates still apply. Report overdue or unverifiable triggers separately from active work.

## Completeness and mixed-status issues

- Issues represent acceptance of a feature or work goal; PRs represent a specific reviewable source or documentation slice. A PR's status describes its own scoped deliverable, not all work under the parent issue. Normally one status label per PR. Keep proposals needing design or unfinished code in draft; use non-draft for actual review-ready scope, not as a substitute for a status label. Native draft/mergeability/green CI alone never establish readiness. Unimplemented ideas normally belong in issues, not new PRs.
- A single-slice issue carries one current status. For mixed-scope issues, maintain an explicit current checklist/table of individually actionable slices with stable identifier, acceptance criteria, status, owner, dependency, linked PR/child issue, evidence and next action. Project the distinct statuses of all unfinished slices onto the parent as status labels so no approved available slice is hidden behind a blocked sibling. Remove a projected label only when no unfinished slice has that status. Reserve the parent's `status: complete` for all accepted criteria; completed slices stay recorded in the checklist. Use linked child issues when slices warrant independent ownership or acceptance; reuse existing workstreams rather than splitting for bookkeeping alone. A parent label is a queue candidate, not authority to start every slice.
- Track objective counts by slice state, not subjective percentages. A source-complete foundation, subsystem merge, pack integration, build availability and gameplay acceptance are different milestones. If only a subsystem PR has merged, record its successor and keep the issue at the actual remaining stage; do not advance to awaiting-build until the required final integration baseline contains the slice. Non-runtime deliverables may complete on accepted evidence without artificial build/QA states.
- Persistent administrative trackers, ledgers and command consoles without a finite feature deliverable must explicitly identify their record type and be excluded from actionable feature counts; their actual finite work items still require statuses.

## Independent research, documentation and QA evidence deliverables

- Research findings, design documentation recording approved decisions or clearly identified proposals, and completed QA evidence are independently mergeable deliverables. Do not require a subsequent coding pass, implementation of recommendations, resolution of downstream owner choices, or new runtime QA to merge a completed evidence-only scope.
- At research completion, the researcher may self-verify the scoped deliverable and hand it directly to the designated integration writer as `status: ready-for-integration` without an intermediate coding or review queue. Record exact current head, scoped questions answered, sources and version/snapshot provenance, evidence checks and limitations, target and dependency order. Applicable required quick checks and local merge authority remain mandatory; if evidence verification remains outstanding use `status: needs-review`, if investigation is unfinished use `status: needs-research`, and if an external dependency prevents completion use `status: blocked`. A completed historical snapshot may be merged as such if clearly dated and not presented as current.
- Separate downstream implementation, owner decisions and runtime acceptance into existing linked issue slices; keep their actual status. Research findings may be accepted even when the conclusion is negative or a recommendation is deferred. Do not claim approval of proposals, runtime acceptance or release authorization by merging evidence. Mixed runtime/code changes must meet their own engineering gates; documentation-only scope is not a way around them.
- No additional research-specific status labels are required: use the existing status vocabulary, with optional orthogonal type labels only when useful for filtering. On merge, close a fully accepted research-only issue; leave broader feature issues open at the remaining slice states.

## Mandatory transitions and handoff

1. At creation/triage, classify each issue and PR and identify acceptance criteria, owner, next action and dependency. Search existing work before creating another branch or PR. An unknown state is needs-triage, not ready-to-code.
2. After a decision or research result, record evidence and immediately promote newly approved actionable slices to ready-to-code (or their actual remaining blocker). Claim a ready slice with named writer and PR/workstream, then mark coding; transfer ownership explicitly.
3. After implementation, move to needs-review until required evidence is available, then ready-for-integration only with exact SHA, approved scope, quick-check results, target, dependency order and next writer. If the head, dependency or evidence changes, reassess and regress status when needed. A stacked handoff must state prerequisite order and unresolved blockers; no label bypasses review, required checks, ownership or local authority.
4. After actual integration, close the merged PR through normal lifecycle; update the issue slice and successor/provenance. Close superseded donors only after verified preservation and dependency reconciliation; never merge stale source just to close a PR. Do not leave PRs open solely for runtime QA.
5. Move integrated runtime-dependent slices to awaiting-build, then ready-for-qa only on verified available candidate and applicable authorization. Record exact candidate, setup, expected behavior, evidence and remaining cases. On failed QA return the affected slice to the appropriate development/research/blocked state. On acceptance mark complete and close the issue only when all criteria are satisfied. Preserve QA/build/release authorization and ref retirement rules.
6. At every decision, coding checkpoint, review, integration, QA result, ownership transfer or closure, reconcile labels, the current description/checklist and canonical ledger. Use the actual current state, not old titles/comments or inferred evidence. Record discrepancies and resolve them with the responsible writer. Closed merged/superseded PRs preserve their final handoff and disposition; they are not active queue entries.

## Queue reconciliation and reporting

The canonical ledger retains the detailed evidence; GitHub labels are the searchable routing index. Live agents and scheduled reconciliation must use both, plus current PR/branch/check and integration evidence. Existing ledgers and gravekeeper/integration audits should reconcile rather than repeatedly recreate classification. Initial adoption requires an evidence-based pass over open issues and PRs, prioritizing decision, code and integration queues; ambiguous legacy work goes to needs-triage, never guessed ready. Report missing labels, contradictory states, unclaimed ready work, stale claims, and exact blockers with owner and next review; update authorized classifications without duplicating workstreams.

Provide separate actionable decision, research, available coding, integration-ready and QA queues, with active coding, review, blocked, deferred, awaiting-build and triage counts separately. Deduplicate by workstream/slice (parent issues and linked PRs are not additional features), distinguish subsystem versus final integration, and retain existing PR throughput and cleanup-debt reporting. A mixed parent can appear in multiple queues for different named slices. A status is not permission to expand approved scope, bypass checks, run a build, publish, delete refs or override single-writer rules.
